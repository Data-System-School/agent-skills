# Verify Generated or Changed Code

## Goal

Assess which correctness claims are supported under explicit conditions. Seek evidence
that can disprove the implementation; do not act as an advocate for it.

## Establish the oracle

Before relying on the implementation or author-written tests, identify independent
sources of intended behavior:

- explicit requirements and acceptance examples;
- public API, protocol, schema, and compatibility contracts;
- domain invariants and security or data-integrity rules;
- stable prior behavior or a trusted reference implementation;
- production traces, fixtures, or externally controlled conformance suites.

If no independent oracle exists, assess internal consistency and regression risk, but
state that intent-level correctness cannot be proven.

## Build the verification matrix

Define behavioral claims before closely following the patch when feasible:

| Behavioral claim | Independent oracle | Implementation path | Check | Negative control | Result |
|---|---|---|---|---|---|

Include success, boundary, invalid-input, permission, retry, concurrency, partial-failure,
state-transition, serialization, compatibility, migration, and rollback claims according
to consequence.

## Avoid correlated evidence

Treat tests generated by the same AI or based on the same implementation explanation as
correlated evidence: both may encode the same misunderstanding.

For higher-assurance work, use an independent verifier that receives the raw requirement,
public contract, base repository, and necessary domain rules without receiving the first
investigator's conclusion. Freeze holdout cases before using their failures to revise the
implementation. Reconcile conflicting conclusions by evidence, not by majority vote.

Do not add tests or alter the repository unless the user requested a change. You may
design candidate cases, run existing safe checks, or use isolated temporary artifacts
when allowed.

## Verification ladder

Choose checks according to risk and oracle strength:

1. Inspect types, contracts, schemas, configuration, and reachable paths.
2. Run typecheck, lint, compile, static analysis, and focused existing tests.
3. Exercise component and integration boundaries with representative and negative cases.
4. Compare base and head behavior under identical inputs and environment.
5. Use property-based checks for invariants and input spaces.
6. Use metamorphic checks when exact outputs are hard to know but relationships between
   executions should hold.
7. Use differential checks against a trusted implementation or prior version.
8. Test the test with a negative control or mutation: introduce or simulate a relevant
   fault and confirm the check detects it.
9. Observe runtime traces or production-like behavior when static evidence is insufficient.

Coverage measures execution, not assertion quality. A high coverage number is not an
independent oracle. Zero static warnings also does not prove runtime, configuration, or
external-boundary correctness.

## Calibrate the conclusion

- Separate specification clarity, source evidence, runtime evidence, oracle strength,
  environment similarity, and unexplored impact.
- Mark flaky, skipped, timed-out, unavailable, or credential-blocked checks. Do not
  silently discount them.
- Reserve human approval for high-consequence changes involving authorization, payments,
  secrets, destructive data operations, migrations, concurrency, or safety boundaries.
- Do not give an uncalibrated numeric probability of correctness.

Use a conditional conclusion:

> At revision X in environment Y, checks P and Q support claims A and B. Claim C and
> external dependency D remain unverified; therefore the current recommendation is Z.

Recommend the next check by expected information gain, not by checklist length.
